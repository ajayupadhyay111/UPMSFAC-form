🔴 Security

S1 — Login secret = sequential, public RegistrationId CRITICAL PARTIAL FIX

What Login = Phone + RegistrationId; the registration code is the password (AuthController.cs:45,110). It was generated from a SQL sequence starting 1000001 incrementing by 1 — fully predictable (AH91000001, AH91000002…).

Why bad The "secret" was guessable and is also the public identifier (embedded in application numbers AH9…-N and the JWT rid claim). PBKDF2 hashing of a low-entropy public value is security theater.

Prod risk Attacker with a target phone (or any leaked application number) enumerates the small code range → account takeover → access to institutional & financial documents.

Fix applied Registration code is now high-entropy random (AH9 + 8 crypto-random base32 chars). This kills practical enumeration while keeping the exact login flow (Phone + code) unchanged. Residual (NOTED) The code still doubles as the public application-number prefix, so a leaked application number still reveals the credential. The real fix (separate the public identifier from the login secret, or add OTP/2FA) changes the product flow and needs a product decision — deferred deliberately.

S2 — No rate limiting / lockout on auth HIGH FIXED

What login/register had no throttle.

Why bad Combined with S1 → brute force & mass enumeration trivial; register spam bloats the DB.

Prod risk Credential stuffing, enumeration, DoS.

Fix applied ASP.NET fixed-window RateLimiter — a generous "auth" policy (per-IP) on /api/auth/*. Normal users unaffected; automated abuse gets 429.

S3 — JWT key silently falls back to hardcoded dev key HIGH FIXED

What If Jwt__Key was unset the app ran with a public dev key (Program.cs).

Why bad A prod misconfig wouldn't crash — it would sign tokens with a known key → anyone can forge a valid JWT for any account.

Fix applied In Production the app now fails fast if the key is missing or <32 chars. Development keeps the convenience fallback, so local runs are unaffected.

S4 — CORS default = allow any origin MEDIUM FIXED

What With Cors:Origins unset the policy allowed every origin, header, method.

Fix applied Permissive only in Development. In Production, cross-origin is allowed solely for configured Cors__Origins; with none set, no cross-origin is permitted (the hosted client is same-origin, so the normal deployment is unaffected).

S5 — File upload trusts filename extension & client content-type MEDIUM FIXED

What Only the filename extension was checked (Steps.cs:27); the client-supplied content-type was stored and re-served, PDFs inline.

Why bad Anything could be uploaded as .pdf; inline serving + client MIME = content-sniffing / stored-XSS surface.

Fix applied Magic-byte sniffing (PDF %PDF, ZIP PK) rejects mismatched content; content-type is now server-derived (not client-trusted); downloads send X-Content-Type-Options: nosniff and default to attachment for non-PDF. Note AV scanning (ClamAV) still recommended for a public deployment.

S6 — No server-side token revocation LOW-MED NOTED

Stateless JWT, 12h expiry, logout only clears the client. A leaked token stays valid until expiry. A real fix (refresh-token + revocation list) trades away the stateless/horizontally-scalable property the design relies on — deferred as a design decision.

✔ Good: EF parameterizes all queries (no SQL injection — the one raw query has no user input); PBKDF2 100k iterations + timing-safe compare; per-request ownership checks; Swagger gated to Development.

🟠 Database Layer

D1 — Phone uniqueness race (no unique index) HIGH FIXED

What Register did a AnyAsync(Phone==) check then insert; Phone had only a non-unique composite index.

Why bad Two concurrent registrations with the same phone both pass the check and insert → duplicate accounts → ambiguous login.

Fix applied Added a unique index on Phone (EF migration AddPhoneUniqueIndexAndHardening) and catch the unique-violation → friendly 409 instead of a 500.

D2 — ApplicationNumber generation race → unhandled 500 MEDIUM FIXED

What ApplicationSequence += 1 then build AH9…-N (ApplicationsController.cs:82); two concurrent creates collide on the unique ApplicationNumber.

Fix applied Create now catches DbUpdateException and returns a clean 409 asking the user to retry, instead of a raw 500.

D4 — EF concurrency exception never handled MEDIUM FIXED

What Application.RowVersion is a [Timestamp]; EF throws DbUpdateConcurrencyException on a conflicting save, uncaught anywhere.

Fix applied The new global exception handler maps concurrency/update conflicts to 409 with a reload-and-retry message.

D5 — Static lookups hit the DB on every request LOW-MED FIXED

What Districts / Councils / Courses are static but were queried every call.

Fix applied Wrapped in IMemoryCache (24h). No behavior change — the data never mutates at runtime.

D3 — Auto-migrate on every startup → multi-instance race MEDIUM NOTED

Every instance runs Migrate() at boot (Program.cs:59). Fine single-node; on the README's claimed horizontal scale-out, concurrent migrations race. Proper fix = a dedicated migration step in CI/CD. Left as-is because the whole one-command deploy currently relies on startup auto-migrate — changing it is a deployment-process decision, not a code bug.

D6 — SQL Server Express vs ~400-user claim MEDIUM-HIGH NOTED

docker-compose.yml uses MSSQL_PID: Express (1 GB RAM, ~10 GB DB cap). Won't sustain the stated load. Move to Standard / managed (Azure SQL) for production. Infra/licensing choice — not changed here.

✔ Good: registration numbers from an atomic SQL sequence; EnableRetryOnFailure; FK columns auto-indexed; explicit decimal precision; one SaveChanges per operation = implicit transaction.

🟡 API & Backend

A2 — No global exception handler MEDIUM FIXED

What Unhandled exceptions (DB conflicts, claim parse) surfaced as raw 500s.

Fix applied Added UseExceptionHandler middleware that returns the same { message } shape the client already understands (concurrency/unique → 409, else 500) and logs the error — no client-side parsing change.

C4 — ApplicantId parse could 500 instead of 401 LOW FIXED

int.Parse(...!) on a missing/garbage claim threw (ApplicationsController.cs:18). Now TryParse → 401 via a typed unauthorized exception.

A3 — Mock payment always succeeds HIGH NOTED

Intentional placeholder (Steps.cs:125). Real-money production blocker — replace Pay() with a real gateway. Left intentional per the project's own README note.

A1 — Inconsistent error response shape MEDIUM NOTED

Custom errors use { message }; [ApiController] auto-validation returns ValidationProblemDetails. The client already tolerates both. Unifying everything to ProblemDetails would change the 400 contract and risk the client's error display — deferred to avoid breaking the working flow.

A4 / A5 — No health check / observability; no client retry policy LOW-MED NOTED

Add /health + structured logging server-side and Polly retry/timeout client-side. Additive, low risk — recommended next.

🟢 Architecture & Code Quality

C3 — Hardcoded fee magic numbers LOW-MED FIXED

400000m / 18m lived in the controller and DTO. Centralized into a single FeeRules constant set (same values) so the fee is defined once.

C1 — Fat controllers, no service layer MEDIUM NOTED

Business logic (short-form detection, snapshot-copy, state transitions) sits in controllers (ApplicationsController.cs:62-114) → hard to unit-test, SRP violation. Extracting an ApplicationService is the right move but a large refactor that touches the whole working flow — deferred to keep this pass safe.

C2 — Heavy duplication (Part1/Part2 mapping ×3) MEDIUM NOTED

Field-by-field copy repeats in Map, SavePart1/2, and CopyPart1/2. Adding a field means editing 3-4 places. Consolidating mapping is recommended but large-surface; deferred this pass.

C5 — Short-form shares the same physical file path LOW NOTED

CopyDocument reuses StoredPath (ApplicationsController.cs:382). Latent: a future delete on one app could break another. No deletion path exists today — documented for when one is added.

✔ Good: clean 3-project split with shared DTOs; proper DI; hosted-Blazor single deployable; readable, well-commented, consistent naming.

🧪 Testing

No tests at all HIGH NOTED

No unit / integration / E2E / regression tests, no coverage, no static-analysis config. The biggest production-confidence gap alongside S1. NextRegistrationSeqAsync uses raw SQL, so integration tests need SQLite/Testcontainers rather than the InMemory provider. Recommend bootstrapping a test project next (this pass was verified manually end-to-end instead).
